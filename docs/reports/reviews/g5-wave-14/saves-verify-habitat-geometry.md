# Wave 14 saves and determinism verification: habitat-geometry

Verifier: saves and determinism lens only. No tracked file was edited except this report. Probes and logs are in `tmp/verify-saves-g5-wave-14-0/` (git-ignored). The HEAD tree was extracted there with `git archive HEAD`; no checkout was used. Verdict: **ok** (no BLOCKER or MAJOR).

## Problems (most severe first)

- MINOR [lead] src/persistence/saveFile.ts:385 — The import checks a save's recorded habitat with `HabitatSchema` only. The new semantic rules live only in the content validator (`recipes.ts habitatShapeProblems`): unique region ids, the anchor inside its shape, inside the dish and on an open cell, and a community group's region existing. A forged save (checksum recomputed) therefore still loads in three cases: two regions with the same id, a region anchored at (0,0), and a Suggested Community naming an unknown region. host.ts `info()` (3355-3360) then passes those regions to `DishInfo.regions`. The result is a pin drawn off the dish and duplicate `key={r.id}` entries in `RegionLegend.tsx:18`. The simulation never reads regions, so stateHash and the outcome are unaffected. — Repro: `tmp/verify-saves-g5-wave-14-0/probes/p3-wafer.test.ts` "import tampering" prints `dupRegionIds: LOADED`, `anchorOutsideDish: LOADED` and `communityUnknownRegion: LOADED`. Suggested fix: run the region subset of `habitatShapeProblems` on load, and refuse with a message that ends "Nothing was loaded."
- NIT [lead] src/persistence/saveFile.ts:385 — The refusal for a bad recorded habitat reads "The habitat definition is invalid." It does not end "Nothing was loaded." The wording predates this wave, but the message now also covers the new fields: 7 regions, a furnish structure S99 and an object material M99 are each refused with it, and nothing is built.
- NIT [habitat-geometry] src/sim/recipes.ts:263-266 — `withHabitatOverride` now drops the recipe's lid, lightMode, drying, baseLight, ops, removeStones, edges and devices for *any* recipe moved to another habitat, not just FIRST_DISH_V1. 18 of the 36 (shipped recipe × {GEL_COLONY, SEDIMENT_EDGE}) combinations realize differently from HEAD; one of them, FUNGAL_SUPPLY_LINE_V1 on GEL_COLONY, is now refused. The UI cannot reach this: the only habitat starts use FIRST_DISH_V1 with `empty`, and every such start is unchanged. host.ts `build()` and `recipeFileProblem` do accept any recipeId with a habitatId, so a hand-made recipe file would rebuild differently than it did at g5 HEAD. No save is affected, because saves hold state, not recipes. — Repro: `probes/p1-golden.test.ts` keys `other:*` (diff golden-head.json vs golden-cur.json).
