## Problems (most severe first)

- MINOR [android] src/persistence/fsPort.ts:83-88 with src/platform/lifecycle.ts:37-44 — On Android, App 'pause' starts an autosave through the bridge. If the OS freezes the cached process while that save is in flight (Android 12+ freezer), the worker's 30 s timer can fire as soon as the process thaws, before the native answer arrives. PortFsOps then marks the store failed, and every later save says "Saving is stopped until Pixelmeba is restarted" for the rest of the session. Saved data stays safe, but the player loses saving until a restart. This is a device-only risk. Repro (device): run a dish, press Home, wait several minutes, return, then Save. ANDROID_SETUP §10.8 has no such step. Add "background for more than 30 s right after pressing Home, return, save to a slot" to the device test, and have the lead consider resetting the failed state on 'resume'.
- MINOR [android] src/ui/main.tsx:52-62 (Lifecycle use) — On native, only App 'resume' clears `away`; visibilitychange 'visible' is ignored. If the App plugin listener never registers (`wireNativeLifecycle`'s dynamic import rejects; the `void` drops the error) or a 'resume' is missed, the first hidden pauses and saves once and every later absence does nothing. The dish then keeps running while hidden, which is offline growth. Repro (reasoning): make `import('@capacitor/app')` reject, then hide → show → hide; the second hide neither pauses nor saves. Cheap fix: on native, let 'visible' also clear `away` without announcing.
- MINOR [android] src/platform/lifecycle.ts:83-97 — App 'pause' also fires when Pixelmeba's own share sheet or the file picker (Import) covers the activity. Sharing or importing therefore pauses a running dish, autosaves, and shows "Paused while Pixelmeba was in the background…" on return. The line is truthful, but nobody decided this behaviour. Add it to the §10.8 device test (items 6–8) so it gets a decision.
- MINOR [android] src/persistence/capacitorFs.ts:317-332 — When a commit fails before its commit point (ENOSPC on the record or journal write, a torn read-back), its `records/<n>.json.tmp`, `journal.tmp` or new record file stays on disk until the next open. Every retry on a full disk adds another one, so a nearly full device keeps losing space until a relaunch. The old save is intact, so nothing is wrong. Repro: tests/persistence/capacitor-fs.test.ts "torn record" case; `Object.keys(ops.files)` before the reopen still holds the .tmp. Best-effort removal of the commit's own tmp and new record in the catch would fix it.
