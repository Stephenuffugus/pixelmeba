const CORR = {
  type: 'object',
  properties: {
    corrections: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          planLine: { type: 'number' },
          kind: { type: 'string', enum: ['path', 'symbol', 'status', 'version', 'number', 'doc-ref', 'ownership', 'port', 'other'] },
          severity: { type: 'string', enum: ['BLOCKER', 'MAJOR', 'MINOR'] },
          claim: { type: 'string' },
          actual: { type: 'string' },
          evidence: { type: 'string' },
          replacement: { type: 'string' },
        },
        required: ['planLine', 'kind', 'severity', 'claim', 'actual', 'evidence', 'replacement'],
      },
    },
    facts: { type: 'array', items: { type: 'string' } },
    notes: { type: 'array', items: { type: 'string' } },
  },
  required: ['corrections', 'facts', 'notes'],
}

const CHECK = (s) => `${CONTEXT}

YOUR SECTION: docs/agent/g3-plan.md lines ${s.lines} — ${s.what}. Read the whole plan header (lines 1-35) for context, then your section in full.

Check EVERY concrete claim your section makes about the repository or the canonical docs, against HEAD:
1. Paths: every file named (to read, to own, SHARED, or "new"). Does it exist? Was it renamed or split (e.g. Lab tray files, NewDish, Notebook, src/ui/journal.ts, atlas feature layers, grid/structures placement helpers that waves B/C created)? Does a file the plan calls "new" already exist (a builder would clobber it)? Give the exact current path.
2. Symbols: every function, type, constant, command, RNG stream, reason code, column, protocol message, overlay id, content ID, test helper and npm script named (e.g. setLid, habitatGrid, buildSpeciesTable, registry(), NEG_ONE_DEFAULT, COLUMNS_ADDED_IN, migrateWorldState, checkAtlas, StateHasher, stateHash, FILM_DIGESTION_IMPLEMENTED, FOOD_OBJECT_CAP, FUNGAL_CAP, NativeAbility, StarchRules, validateContent, buildSaveFile, loadSaveFile, worldContentFor, allocateFields, expectNoSeriousA11yViolations). Does it exist with that name and a compatible signature? If not, what is the real one?
3. Status: every "already implemented" / "not implemented" / "verify P2.x built it" claim. Is it still true after waves B/C? (e.g. shade paint ×0.1 and erase, the Lab trays and their categories, structure placement, overlay picker, protocol version number, atlas feature table keyed feature/<layer>/<heading>/<frame> from D-0032, the journal and Notebook from D-0027/D-0031, checkpoints.)
4. Versions: schemaVersion (plan says 3 → must be 4), contentVersion, buildPhase, moduleRegistryVersion, evolutionRulesVersion, protocolVersion, atlas manifest version — what are they at HEAD and what should the plan say?
5. Numbers: every number your section's prompts state as a rule (rates, caps, thresholds, doses, radii, coordinates, frame counts, colours) — does it match docs/CONTENT_TABLES.md / docs/PIXELMEBA_IMPLEMENTATION_SPEC.md / docs/UX_SPEC.md / docs/ARCHITECTURE.md? Quote the doc line for any mismatch. Spot-check doc section references (e.g. "CT §8.1", "SPEC §9.19", "D04 §2 row C08") point at the right content.
6. Ownership: within your wave, are two builders given the same file to own, or a SHARED file edited non-additively? Does a builder own a file that Phase 2 now uses heavily in a way the prompt ignores?
7. Anything else that would mislead a builder who follows the prompt literally (e.g. a test file name that collides, a port clash inside the wave, a step that is now redundant because Phase 2 already did it).

Return corrections (planLine = the plan line where the claim is; claim = what the plan says, quoted briefly; actual = what is true at HEAD; evidence = command + output excerpt or file:line; replacement = exact text the lead should put in the plan; severity BLOCKER = a builder following the plan would break the build/saves/determinism or clobber work, MAJOR = would waste significant time or implement something wrong, MINOR = cosmetic/imprecise). Put in "facts" the concrete current-tree facts a builder of your section will need (exact paths, signatures, current version numbers, names of existing helpers) — short lines. "notes" for anything else. Do not pad: if a claim holds, say nothing about it.`

const VERIFY = (s, found) => `${CONTEXT}

A checker compared docs/agent/g3-plan.md lines ${s.lines} (${s.what}) with the committed tree and claims these corrections are needed:
---
${JSON.stringify(found.corrections, null, 1)}
---
and these facts:
---
${JSON.stringify(found.facts, null, 1)}
---
You are the skeptic. For EACH correction, independently re-check the plan line and the tree/docs and try to REFUTE it: is the plan actually right (e.g. the path exists under another command, the symbol exists with that name, the number matches the doc)? Is the replacement text itself correct and complete? For each fact, check it is true at HEAD. Also look quickly for important errors the checker MISSED in that section (same rules: paths, symbols, status, versions, numbers, ownership). Return "corrections" = the corrections that HOLD (fix their replacement text if it was wrong) plus any you found that were missed (mark those with "MISSED: " at the start of claim); "facts" = the facts that hold (corrected where needed); "notes" = one line per REFUTED correction or fact saying why.`

const results = await pipeline(
  SECTIONS,
  (s) => agent(CHECK(s), { label: `check:${s.key}`, phase: 'Check', schema: CORR }),
  (found, s) => (found ? agent(VERIFY(s, found), { label: `verify:${s.key}`, phase: 'Verify', schema: CORR }).then((v) => ({ key: s.key, lines: s.lines, found, verified: v })) : { key: s.key, lines: s.lines, found: null, verified: null }),
)

phase('Synthesize')
const bundle = results.filter(Boolean).map((r) => ({ section: r.key, lines: r.lines, corrections: r.verified ? r.verified.corrections : (r.found ? r.found.corrections : []), facts: r.verified ? r.verified.facts : (r.found ? r.found.facts : []), refutedOrNotes: r.verified ? r.verified.notes : ['NOT VERIFIED (skeptic missing)'], checkerNotes: r.found ? r.found.notes : ['CHECKER MISSING'] }))
const missing = results.filter((r) => !r || !r.verified).map((r) => (r ? r.key : '?'))
if (missing.length) log(`sections without a verified result: ${missing.join(', ')}`)
const doc = await agent(`${CONTEXT.replace('STRICTLY READ-ONLY: do not create, edit or delete any file in the repository;', 'You may create exactly ONE file: docs/agent/g3-plan-recheck.md (nothing else);')}

Write docs/agent/g3-plan-recheck.md: the verified corrections to docs/agent/g3-plan.md after Phase 2 waves B/C, for the lead to apply when writing docs/agent/g3-wave-{1..6}.workflow.js.txt. Structure: a short header (date 2026-09-29, HEAD at the time: run "git log --oneline -1", method: read-only checker + skeptic per section); "Global corrections" (anything that applies across waves — schema 4, version numbers, renamed paths used in several waves — deduplicated); then one section per plan section (preflight, wave1 … wave6) with a table: plan line | severity | plan says | actually | replace with; then "Facts builders need" per section (deduplicated, exact paths and signatures); then "Refuted by the skeptic" (one line each, so the lead knows what NOT to change); then "Sections not verified" if any. Keep replacement text exact and paste-ready. Do not invent corrections that are not in the data below; you may merge duplicates. Data:
---
${JSON.stringify(bundle, null, 1)}
---
Return a 10-line summary: counts by severity per section and the three most important corrections.`, { label: 'synthesize', phase: 'Synthesize' })
return { summary: doc, missing, counts: bundle.map((b) => ({ section: b.section, n: b.corrections.length, blockers: b.corrections.filter((c) => c.severity === 'BLOCKER').length })) }
